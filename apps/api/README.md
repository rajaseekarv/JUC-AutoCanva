# AdFlow API

NestJS + TypeScript API. Sprint 1 adds login, revocable JWT access sessions, current-user identity, permission guards, and server-side branch authorization. Access tokens are returned only to the authenticated client. The web app saves the token and its expiry in browser storage and revalidates it with `GET /auth/me` after a reload; that endpoint uses the same JWT guard, so a revoked, expired, or inactive-user session is rejected with 401. Refresh tokens are not implemented. The health endpoint remains a public liveness check.

Run from the repository root with `pnpm --filter @adflow/api dev` or use the root `pnpm dev` command to start both applications. The API binds to `127.0.0.1` by default in development; set `API_HOST=0.0.0.0` in the root `.env` only when intentional LAN access is needed. In production, the server retains its existing platform-default bind behavior. `.env` resolution is relative to the API entry point, not the shell working directory. The health endpoint is liveness-only; database and Redis readiness checks are deferred.

Set `JWT_ACCESS_SECRET` to a random secret of at least 32 characters. For local seed data, set `SEED_ADMIN_PASSWORD` and `SEED_BRANCH_USER_PASSWORD` (each at least 12 characters) in the ignored root `.env`, then run `pnpm db:seed`. Passwords are Argon2id-hashed. Failed login attempts remain a future audit coverage item.
Sprint 2 endpoints provide authenticated organization profile access, permission-guarded organization updates, organization-scoped branch management, and permission-guarded user branch access management. All organization scope is taken from the authenticated principal. Branch-restricted users can access only active branches explicitly granted to them; users with `branches:manage` can manage inactive branches within their own organization. No schema migration was required. Organization, branch, and branch-grant mutations write audit events in their database transaction.

## Sprint 3 assets

Brand and asset routes use the existing JWT and permission guards. Uploaded images are limited to valid PNG/JPEG/WebP files up to 5 MB and stored under the repository-local `.local-storage/assets` directory by default. `ASSET_STORAGE_DIR` can set an alternate local root. The storage implementation is isolated behind the `LocalAssetStorage` provider for replacement by a production object-store adapter in a later deployment effort. `GET /api/v1/health` remains a liveness endpoint.
Organization-wide brand edits and asset writes require `organizations:update` in addition to the relevant feature permission. Branch-scoped operations additionally verify the branch belongs to the authenticated organization and that the caller manages or is assigned to that branch.

## Sprint 5 creatives

Creatives require creatives:read, creatives:create, or creatives:update and are always branch-scoped. The service checks organization, active branch status, and explicit branch grants (or same-organization branches:manage) for every read and mutation. Optional campaign links must match an existing assigned CampaignBranch in the same organization and branch. Revisions are append-only in normal APIs; edits create the next revision and advance the pointer in a serializable transaction. Template validation uses the exact immutable version: new creatives/version changes require it to be active, while edits may retain their existing selected version after archival. Image/logo field values are stable asset IDs validated through the asset service against branch scope. Creative and revision writes are recorded in audit history in their transaction.

## Sprint 6 workflows

Workflow definitions are organization-scoped, versioned, declarative JSON configurations. `workflows:manage` controls definition lifecycle; `workflows:read`, `workflows:start`, and `workflows:transition` are separately enforced. Instance endpoints verify organization and branch access on the server. Starts require an explicit enabled workflow ID and pin the current or explicitly selected revision. `GET /api/v1/workflow-instances/:id/transitions` returns only outgoing actions permitted to the caller. Transition requests accept a stored transition key, and update stage, `Creative.status` projection, task state, and append-only history in one serializable transaction. The latest instance stage is authoritative, and Creative.status remains its projection after terminal completion. A partial unique index allows only one running instance per creative. Creative edits conflict while an instance is running. Disabling blocks new starts while existing instances remain on their pinned version.

## Sprint 7 approvals, comments, and change requests

Review stages set `requiresReview: true`, use exactly one assignment (user ID or permission code), and tag decision transitions with `reviewDecision: "APPROVED"` or `"CHANGES_REQUESTED"`. A specific-user assignment requires that user; a permission assignment is one task completed by the first eligible user. Each task accepts one decision. Ordinary transition calls cannot leave a review stage. `GET /api/v1/approvals/tasks` lists authorized pending assignments; `GET /api/v1/approvals/tasks/:taskId` returns the pinned revision context; `POST /api/v1/approvals/tasks/:taskId/decision` accepts a decision and an optional reason (required for changes requested) plus an optional explanation for the resulting change request. Decision, task completion, optional change request, workflow transition, and history commit atomically.

Decision history is available from `GET /api/v1/creatives/:creativeId/decisions`. A changes-requested decision creates an immutable-text change request tied to its exact original revision, available from `GET /api/v1/creatives/:creativeId/change-requests`. Requests can move from OPEN to IN_PROGRESS using `POST /api/v1/change-requests/:id/start`, and can be explicitly resolved or cancelled through `POST /api/v1/change-requests/:id/resolve` and `/cancel`; later revisions do not resolve them automatically. Revision comments are listed/created at `/api/v1/creatives/:creativeId/revisions/:revisionNumber/comments`; comments are append-only, whitespace-only text is rejected, and replies must target the same revision. All operations enforce organization, branch, permission, reviewer, task, and revision relationships on the API. Seeded administrators receive all review permissions; branch operators can read/decide reviews, create/read change requests, and read/create comments, but cannot resolve/cancel requests. Critical review mutations write audit events and scoped in-app notices in the same transaction. Direct reviewer assignments notify the assigned user; permission-only assignments do not broadcast.

## Sprint 8 audit and notifications

Audit endpoints are `GET /api/v1/audit-logs` and `GET /api/v1/audit-logs/:id` and require `audit:read`. The seeded organization administrator receives this permission; queries are organization and permitted-branch scoped. Audit metadata is capped and validated against sensitive key names, and no update/delete API is exposed. Authenticated notification endpoints provide list, unread count, detail, mark-read, and mark-all-read, always scoped to the caller's user ID. Notifications are idempotent by recipient and event key.
